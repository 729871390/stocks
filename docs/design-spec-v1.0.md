# 投资信息中台设计方案 v1.0（原始规格，自上传文档提取）

投资信息中台设计方案
信息源 · 信息流 · 日报 三模块实现参考 ｜ v1.0 ｜ 2026.07
本方案取自一套已上线运行系统的实际形态，含全部数据模型、管道规则、页面规范与工程红线，可直接照此实现。

〇、总览：一个宽进严出的信息漏斗
三个模块构成一条流水线：信息源（宽进：多渠道抓全）→ 信息流（加工：去重、分级、打标、聚类，全量可检索）→ 日报（严出：每天只把最值得读的东西推到人面前）。核心理念是把"筛选高质量信息"自动化——原始信息不设限地进，交付物极度克制地出。
0.1 技术底座参考
组件
选型与理由
运行时
Node.js 22 ESM，三进程（Web 服务 / 表驱动调度器 / 异步任务 worker），pm2 托管
存储
SQLite 单文件（WAL 模式）+ FTS5 全文索引。单机单写场景下免运维、原子写、全文检索一体；不要用云数据库
调度
node-cron，任务表驱动（cron_jobs 表：表达式/时区/启停/run_once/历史），管理界面可控；每任务独立时区
模型分档
三档：分级档（廉价快速模型，海量小任务）/ 主力档（推理模型，深读成稿）/ 轻量档（标题、归类、摘要类 JSON 小任务）。分级绝不用贵模型
抓取
RSS 用 rss-parser；X 无 API 时可用搜索型 LLM（如 Grok）按账号批量抓取；YouTube 用频道 RSS 发现 + yt-dlp 拉字幕（不做 ASR）
0.2 全局设计原则（三模块共守）
渠道适配器：每个渠道实现 discover(source)→raw[] 与 fetch(raw)→统一条目结构 两个函数并注册；下游管道（去重→分级→打标→聚类→日报）只消费统一条目结构，对渠道零感知。新增渠道 = 一个适配器 + 注册表一行 + 添加表单一种类型，不改任何下游代码。
字段写入契约：每个状态字段有且只有一个写入函数，其他代码路径禁止直写；字段新增必须写明四要素——唯一写入点 / 写入时机 / NULL 语义 / 存量回填策略。
Schema 变更三件套：迁移脚本 + 存量回填脚本 + 一致性断言（纳入每日自检），缺一不上线。
一处定义、多处消费：渠道枚举、行业标签、行为标签、分级标准全部单点定义（注册表 / prompt 文件），管理页与筛选面板从同一定义渲染，禁止两边各自维护。
时间铁律：任何日期入库前归一化为 UTC "YYYY-MM-DD HH:MM:SS"（RFC-2822 原样入库会击穿 SQLite 字典序比较，导致过滤恒真、排序错乱）；展示层统一经 Intl 按目标时区渲染，禁止用浏览器/服务器本地时区直出。
全量可见原则：信息流默认展示全部抓取条目；唯一允许隐藏的是"真重复"（同一内容多载体合并后的冗余条）。分级只影响徽标、排序与筛选，不影响可见性。

1.2 健康可观测（判定规则全文）
三时间戳语义分离：last_attempt_at（调度有没有轮到）/ last_success_at（链路通不通）/ last_new_item_at（源本身活不活跃），三者各答一个问题，禁止混用。
铁律：低活跃 ≠ 故障。last_new_item_at 永不参与 failing/dead 判定——账号两个月不发推但抓取成功，状态就是 ok；超 30 天无新内容只出灰色 idle 提示徽标，不进故障统计。
错误三分类：permanent（404/410/账号不存在/凭据失效 → 立即 dead）；transient（超时/5xx → 计入 fail_count）；ratelimit（限流 → 不计数只留痕，防批量抓取触发限流时整批误判）。
状态按"错误类型 + 距上次成功的时长（以该源抓取周期为单位）"推导，不按固定失败次数：failing = 有 transient 失败且距上次成功超 3 个周期；dead = permanent 或超 10 个周期或从未成功且创建超 10 周期。周期倍数与 idle 天数全部进 config，禁止硬编码。
告警分级：普通源 dead 才告警；核心源（P0）failing 即告警。
1.3 抓取节律与初始化
全部信息源每天两班：湾区 06:30 + 北京 06:30，各自本地时区调度（每任务带 tz，夏令/冬令自动），保证两地 07:30 前"抓取+分级"全部就绪。
抓取后链式分级：任一抓取任务成功即触发分级任务（run_once），不等整点——信息流不允许出现"抓到了但没总结没打标"的积压窗口。
新源提交即初始化：立即首抓，回填 = 最近 20 条 ∩ 不早于 90 天双截断（防 Podcast 全量历史归档污染，实测有 feed 一次吐 587 条陈年 episode）；90 天截断提升为入库层全局规则。行内进度反馈"初始化中→已入库 N 条/失败原因"。
1.4 管理页 UI 规范
主视图 = 按渠道分组的卡片网格（每行 4 张，等高）：卡片只有复选框、源名（外链到 site_url，点击不冒泡）、最新更新时间三样；故障源右上角红点、停用置灰。详细指标全部收进点卡片打开的详情弹窗，不占主视图。
详情弹窗三区：基本信息可编辑（名称/行业/角色/优先级/备注）；诊断只读（状态、双时间戳、失败原因、30 天统计、下次调度时间——停用则显示"已停用，不参与调度"、最近 3 条变更记录）；操作（启停/删除/测试抓取）。
启停可验证四层：①禁止乐观更新——后端返回变更后的真实状态，前端只按响应渲染 + toast；②停用即时移出调度集合，"下次抓取"字段随之变化（可视证据）；③测试抓取按钮无条件拉最近内容回显"连通 ok · 取到最近 N 条 · 最新一条：标题（日期）· 新入库 M 条"；④每次启停/删除写审计日志。
添加 = 按钮+弹窗：单条模式按渠道动态出字段；批量模式贴一堆链接/handle 逐行自动识别（YouTube 链接解析 channel_id、X 提取 handle、其他 URL 探测 feed 或 <link rel=alternate>），预览列表可改名，失败行标红原因，确认后只建通过行。
批量操作条内嵌在筛选行下方（不用浮窗）：双态按钮（全启用→"停用"/混合→"全部启用"+计数小字）、核心/标准双态、删除独立红色需确认。
1.5 数据不变量每日自检（防复发机制）
每日 cron 跑断言清单（名称+SQL+说明的可扩展结构），任一违反即 IM 告警并在系统设置页展示结果。起步断言：有条目的源 last_new_item_at 不得为 NULL；缓存时间戳必须落在真实数据范围内；条目无悬空外键；published_at 全部 ISO 格式；可见条目分级覆盖率 100%；统计表新鲜度 ≤48h。每次 schema 变更的三件套断言追加进来。

事件聚类（弱合并，只折叠不并正文）：规则① 核心实体重合≥2 且标题连续公共串≥6 字；规则② 同频道视频/播客 48h 内标题相似度≥0.3（同期节目切片拆条发布场景）——规则②严禁用于新闻源，同天多稿常提同一公司，误并风险高。
强合并（同内容多载体，合并正文）：标题规范化二元组相似度≥0.9 + 发布时差≤48h + 公司标签交集 → 保留最完整版本（全文源优先），其余 hidden + 记 also_seen_in。阈值进 config；上线前先跑存量预演清单人工抽查，确认无误伤才启用。指路型推文（短文+链接）展开后必须采纳链接的 canonical，否则同链接的第二条永远合并不上。
2.3 展示规范
默认视图：全部条目、不设时间窗；纯抓取时间倒序（簇折叠行用簇内最新抓取时间排序与显示，避免主条目较旧造成视觉乱序）；时间显示"月-日 时:分"绝对格式、强制目标时区（Intl，与浏览器时区无关）。
无显式等级筛选时只展开 3 级及以上，1-2 级折叠为一行"另有 N 条低等级条目"一键展开；未分级条目照常显示（灰点徽标，链式分级几分钟内补齐）。
五色等级徽标（20px 圆）：5 砖红实底 / 4 赭橙实底 / 3 主绿实底 / 2 墨描边 / 1 浅灰描边——实底三档值得读，描边两档低价值。全站同源引用。
筛选面板维度：数据源（按渠道分组，与源管理页同一注册表）/ 时间（默认全部）/ 等级 / 标签八类（六行业+融资+人员变动）/ 公司（按行业分组+搜索）/ 渠道 / X 行业 / 角色 / 内容类型 / 源优先级。staged 应用制（选完点应用），状态写 URL 可分享。
搜索 = 标题关键词全量匹配（LIKE），不走全文索引——用户预期是"搜融资出来的全是标题带融资的"。
详情页：AI 标题 + 查看原文按钮 + 元信息行 + 标签行 + so-what + 摘要 + 客观事实 + 同内容载体列表 + 媒体缩略图 + 原文默认折叠（点击展开）。不做"同一事件/相关阅读"推荐区（实测没用）。
三、日报
3.1 定位与时序
日报核心目的是 sourcing，价值排序：①找方向 ②找公司 ③找产品——这句话直接写进深读选择 prompt 开头。每天只在主时区早 07:30 生成一次；数据依赖前置：抓取班次提前一小时（两地 06:30）+ 抓取后链式分级，生成前再等待未分级清零（至多 15 分钟）。调度器启动时检查最近一班应出的日报是否缺失，缺则自动补跑（进程重启撞上班点也不丢班）。
3.2 深读区：固定三槽位

定位
选择

研究类栏目
入选池与五级分级完全一致：先 5 级，不足按 4 级补位，仍无则 3 级取热度最高，再无省略该槽位；同一条目不占两个槽位；owner 钉选 +1000、watchlist 命中 +50、核心源 +40 加权。
热度=事件簇独立来源数 + X 互动量级（log 加权）——只作排序输入，绝不写入正文。
每篇版式：序号（01/02/03）+ 槽位名 + 标题（衬线加粗）+ 两小节：【事件】完整硬事实（金额/参数/价格/日期/当事方一个不落；社媒互动数据点赞转发浏览量绝对禁止，prompt 禁令+正则复检强制重写+兜底剥离三重防线）；【分析】2-3 段连续正文不设小标题（第一段 so-what 传导链条、第二段共识与非共识、第三段观察指标），禁止正文出现"我们的看法/共识与非共识/后续观察点"等栏目词。500-800 字 + 空洞词黑名单（"值得关注/意义重大"类命中即重写）。
观察点结构化数据（日期窗+对象+判断标准）仍让模型输出但不渲染，自动登记进触发点表，到期日在日报头部"触发点回访"回显（句边界截断防切半句）。
3.3 重要信号：六模块定额
固定顺序：Model/Labs → 算力/Infra/半导体 → 软件/Application → 融资动向 → 人员动态 → 研究动态。融资动向一个不落（当日全量）；其余模块各挑 3 条最重要（等级 > 簇规模 > 热度，3 级起）。条目附短链直达库内详情页。
3.4 其余区块

四、工程红线（实现者必读的坑清单）
日期入库必须归一化为 UTC 标准格式。RFC-2822 字符串在 SQLite 字典序比较下"晚于任何 ISO 日期"，时间窗过滤恒真、排序全乱、条目集体沉底——这是实测踩过的最深的坑。
分级队列的窗口条件按抓取时间，不要用 COALESCE(发布时间, 抓取时间)——刚抓回来但发布超窗的条目（老视频、补抓文章）会永远卡在"待分级"。
分级失败要有重试上限（如 5 次止损），否则解析失败的条目每轮重试无限烧 token；推理型模型 JSON 输出必须给足 max_tokens（截断是最常见的静默失败）。
每个状态字段一个写入函数。"卡片显示尚未更新但 30 天条目有 43 条"这类自相矛盾，根因都是字段只定义了语义、没定义写入契约。
限流错误不计入失败计数：批量抓取触发限流时会把整批源误判成故障。
新源首抓必须截断（最近 N 条 ∩ M 天），并把时间截断提升为入库层全局规则——否则订阅一个 Podcast 就是几百条陈年 episode 灌进信息流。
展示层时间永远经 Intl 指定时区渲染。浏览器本地时区直出（getHours/slice 字符串）在跨时区用户面前必错。
同源标题相似度聚类只对视频/播客切片开放。新闻源同一天多篇"OpenAI 发布 X / OpenAI 审计 Y"标题相似度轻松过阈值，开了必误并。
强合并类规则上线前先跑存量预演清单人工抽查；阈值进 config 不硬编码。
前端 HTML 内嵌在服务端模板字符串时，行内事件处理器里的引号与 \n 会被模板求值吃掉——一律用事件委托 + data 属性，改动后用"求值提取 + 语法检查"验证。带行内 display 样式的元素 hidden 属性无效，用 style.display 控制显隐。
禁止乐观更新：启停类操作等后端返回真实状态再渲染，配"测试抓取"这类直接验证手段，用户才信得过开关真的生效了。
推送内容与网页内容同源同规则（一份数据两种渲染），微信长文本语义分条而非字数截断——按字数砍内容用户一定会发现"怎么断了"。
